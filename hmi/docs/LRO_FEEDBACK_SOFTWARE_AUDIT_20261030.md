# LRO 整臂温度与反馈新鲜性：软件审计

日期：2026-10-30。范围：当前工作区、本机安装包及离线故障注入；不包含现场电气测量和硬件验收。

后续状态：以下保留审计时的缺陷与复现记录；其中 B、C 已在后续源码中修正，修改机制、回归与未安装边界见 [温度误显示与旧反馈失效修复](LRO_FEEDBACK_FRESHNESS_FIX_20261030.md)。A 的类型过滤此前已存在于工作区，D 的重复 ID 准入缺口不属于此次修复。

## 结论

上位机确实存在可能显示错误温度或继续显示旧数据的软件路径。已经隔离复现，不能仅凭单测正常把现场根因归结为整臂 CAN 线束，也不能把软件缺陷的复现等同于现场根因已经确认。

1. 本机安装的 3.0.0 原生 LRO 接收代码不区分反馈类型，会把同一 ID、长度至少 8 字节的其他回复当作 type-1 遥测；注入 type-5 回复已复现温度由 46 变为 100，并错误推进遥测计数。当前工作区已有类型过滤，安装库尚未包含。
2. 当前工作区与本机安装版的控制器在快照读取异常时，保留旧样本及旧的反馈年龄。注入一次读取异常后，10 秒前的样本仍以 feedback_age_s=0 发布，界面显示 46.000 和“正常”。
3. 当前工作区与安装版界面在 WebSocket 仍标记连接时跳过备用轮询，没有按最后一条快照到达时间启动降级；静默断流可使显示停在最后值。已经验证相应条件下备用轮询未发出、表格值及正常状态保留；未进行真实网络半开连接实验。
4. 当前工作区对合法 type-1 帧没有温度单独缓存、不更新或固定成 46 的逻辑。5 个 ID、10,000 条交错反馈离线验证通过；一台不回包不会借用其他四台的新鲜时间。

上述第 1 项需要现场确实出现非 type-1 回复才会触发；第 2 项需要读取/刷新抛异常；第 3 项需要状态通道静默。当前没有现场原始报文、异常栈和相应时刻的软件版本，不能宣称已锁定其中任何一项为现场原因。

## 用户条件与尚未核实的现场信息

- 用户确认全部温度读取发生在未使能阶段。
- 同一台电机未作改动，拆离手臂后单测正常。
- 用户提供的分析涉及换电机/终端电阻、右短臂 5 节点、right_wrist_roll 锁在 46°C 和 fresh feedback timeout；本次未取得对应原始报文和日志进行独立对时核验。
- 没有执行实物 CAN/PLC 通信、使能、复位、轨迹或固件更新，没有改动当前运行配置。

## 数据调用链与问题位置

```text
SocketCAN 每条总线的接收线程
  → 按 CAN ID 查找回调
  → LroMotorDriver::canfd_rx_cbk
      更新位置、速度、力矩、温度、故障码及 feedback_count
  → MotorsPyBackend.read_samples
      根据每台电机的计数推进计算 timestamp_s / feedback_age_s
  → FactoryController.snapshot
  → FactoryService / 网关快照
  → WebSocket 或 REST
  → FactoryMainWindow._render_snapshot
      根据快照中的反馈年龄显示数值或“—”
```

### A. 安装版会把其他类型回复当作遥测（已复现）

位置：`hmi/motors/src/drivers/lro/lro_motor_driver.cpp`，`LroMotorDriver::canfd_rx_cbk()`；旧安装版的匹配源码保存在本次审计产物 `installed-source/`。

旧代码仅要求长度至少 8 字节，虽然计算了 `fb_type`，却没有按类型分支。结果是：版本/查询回复或 type-2/3 回复也会被按 type-1 的字节位置解析。温度被赋为 `data[6]-25`，`feedback_count` 同时递增，后端因而也会把这种非遥测回复当作新鲜反馈。

注入证据：先给同一 ID 一条 type-1 帧、`data[6]=71`，显示 46；再给 type-5 帧、`data[6]=125`，旧代码显示 100 且遥测计数加一。注入 type-2 帧也复现使用错误的温度偏移并推进计数。

当前工作区已存在的修正先分离 type-5 查询回复，并仅接受 type-1 进入上述遥测解析。此改动不是本轮新加，且未进入本机 3.0.0 安装库。不能凭工作区已修正就宣称现场生效。

### B. 读取异常后，旧样本仍可能以“新鲜”发布（已复现）

位置：`hmi/factory_hmi/core/controller.py`，`FactoryController.snapshot()`。

未使能时，快照先调用 `backend.refresh_feedback()`，随后 `read_samples()`。任一步抛异常时，`except Exception: pass` 会保留上次 `_last_samples`。`MotorSample.feedback_age_s` 是建立样本时计算的数值，不是随时间自动变化的属性；`to_dict()` 也只原样输出。

故障注入：在单调时钟 100 秒取得 46°C、反馈年龄 0 的样本，在 110 秒令刷新抛出 OSError。快照总时间戳为 110，但电机仍是 timestamp_s=100、feedback_age_s=0；界面仍显示 46.000 和“正常”。当前工作区和安装版 Python 代码均复现。

这条缺陷会让该批保留样本的角度、温度等共同停留在旧值，不能用来解释“同一颗电机的实际反馈角度一直正确更新，只有温度停止”的全部现象。

### C. 实时通道在线但静默时缺少显示过期处理（条件已验证）

位置：`hmi/factory_hmi/desktop/app.py`，`_setup_network()`、`_poll_snapshot()`、`_render_snapshot()`。

备用定时器每 5 秒调用 `_poll_snapshot()`，但 `_ws_connected=True` 时直接返回。界面没有根据最后一条电机快照的本地接收时间累加显示年龄。WebSocket 断开通知到来后会启用降级，但“未收到断开通知且没有新消息”的期间缺少对应降级。

离线测试保持连接标志为真，模拟长时间无新快照并调用备用轮询；没有 REST 请求，表格仍保留最后的 46.000 和“正常”。这是调用条件验证，未模拟真实 TCP、操作系统超时或硬件网关阻塞。

### D. 重复 ID 配置未被拒绝（附加发现）

位置：`hmi/factory_hmi/core/config.py`，`build_station_config()`；`hmi/motors/src/protocol/canfd/socket_canfd.cpp`，`add_canfd_callback()`。

把同一 can1 的五个配置 ID 改为 `[1,2,3,4,1]`，配置构建没有报错；回调注册使用 `map[id]=callback`，重复注册会覆盖前一个。相同赋值方式的假传输验证：前一个对象收不到反馈，后一个收到。默认右短臂配置是 `[1,2,3,4,5]`，本次未发现它自带重复 ID。

此项是配置准入缺口，不等于现场实际存在重复 ID。多个物理设备使用相同 ID 时，即使配置表仅列一次，上位机也不能仅凭 CAN ID 识别发送者；仍需要现场设备身份和拓扑核查。

## 哪些推断不成立，哪些仍待验证

- 当前 type-1 协议中，位置和温度属于同一帧；丢掉该帧会一起失去这次更新，没有单独的“温度字节包”。
- CAN 在帧层做错误检测，检测到错误会丢弃当前消息；不能把线束反射直接解释成“某个温度字节先损坏、其余字节照常正确交给应用”。参考 [Kvaser 官方错误处理说明](https://kvaser.com/lesson/can-error-handling/)。这不排除节点在采样阶段生成错误温度，也不排除软件解释错误或节点归属错误。
- 46°C 在当前解码中对应原始值 71，即十六进制 0x47；100°C 对应 125，即 0x7D。没有发现 46 的固定偏置或锁值常量。
- 如果现场合法 type-1 帧的位置字段持续变化，但温度字段一直是 0x47，上位机就会持续显示 46。帧级新鲜性不能证明设备内部温度传感器已重新采样；恒定温度本身也不是足够的故障证据。
- 如果合法 type-1 的温度字节已经变化、界面仍为 46，才直接支持解析、缓存或显示链路异常。抓包还应记录帧类型，防止把 type-2/5 的 `data[6]` 当成 type-1 温度。
- `fresh feedback timeout` 只证明确认期限内未取得每台电机要求的新反馈次数，不证明一定是带宽不足；也可能涉及设备未回复、发送失败、软件接收阻塞、错误配置等。

## 修复边界与下一步

本轮只完成检查、离线复现和报告，没有新增或修改应用修复，没有安装或启用新版本。当前工作区已有的类型过滤可阻止 A 类误解码；B、C、D 在本轮审计时仍存在。

后续软件修复应分别处理：所有快照出口重新计算缓存样本的实际年龄并记录读取失败；界面按最后快照到达时间降级，避免在线标志代替数据新鲜性；配置和回调注册拒绝同总线重复地址。不得把恒温直接认定为温度传感器故障，也不能为隐藏异常而平滑、替换原始温度。

现场最小取证应在未使能条件下同时保留：请求/回复的接口、方向、时间、ID、长度、反馈类型、完整字节；同一时刻的界面值、反馈年龄、故障码；实际运行版本与原生库哈希。只有取得这些证据，才能区分软件误解码、整帧停止、设备持续上报恒定温度，以及整臂电气条件触发的问题。真实设备联调、错误注入下的长期稳定性和安装生效验证尚未执行。
