# 电机监控版本显示与读取时序（2026-11-12）

基线为 PLC 上位机 v3.0.30。现场截图中 7 台电机有角度和温度反馈，不能据此推断固件查询已成功；使能报 `can0#1 电机协议未确认` 的具体原因仍需版本读回与现场验证。

`factory_hmi/desktop/app.py` 的电机监控表根据 CAN 接口和电机 ID 关联 `motor_versions`，显示原始固件字符串以及已读取、部分读取、超时、未知、不支持、过期等状态。连接后已有 `core/motor_versions.py` 唯一后台线程执行只读版本查询，首轮逐台查询，此后整轮结束等待 60 秒。界面不增加 CAN 查询、使能、固件刷写或参数写入。固件读回不等于协议身份通过核实。断线或快照失效不展示为当前有效读回。

v3.0.30 的 108 默认身份必须得到相符的原始版本；109 的 V1.03 节点仍要求按节点提供实际核实的版本、硬件、协议和证据并逐项匹配。当前未实现从任意 109 版本号直接自动确认协议；不能仅凭数字猜测电机控制报文格式。固件升级、参数检查/写入保持独立入口。保持既有关节测试操作流程以及使能保护。

隔离模拟发现 Python 每次版本读取等待 0.35 秒、SDK 有 0.5 秒响应窗口：模拟在 0.40 秒返回的有效固件查询会因 Python 先发下一项查询而被丢失。此结果是代码层模拟，不足以确认现场报错根因。修改此等待时间须统筹 SDK 接收、使能请求总超时、取消及超时后结果确认，避免客户端超时后后台仍执行使能；超过 SDK 接收窗口的回复仍需要额外设计和真实设备验证。

用户已确认受影响工位测试停止、电机失能、柜内外供电断开并支撑机构；本机通过 v3.0.30 `stop --site-isolated` 正常退出并确认原状态目录 `running=false`。这不等于取得正常 PLC 关断反馈，重新上电或试验需要现场确认并按规程进行。

## 读取等待时间的修复

原生 SDK 的版本回复接收期限为 500 ms，原后台线程等待 350 ms 后即发下一条查询，可能覆盖尚在 SDK 有效期内的查询。现将单条等待延长至 500 ms，取消时不再发送下一项；不修改原生库或超过其接收窗口。模拟在 400 ms 返回的帧可被读取，600 ms 响应不得错认成下一项结果。真实设备是否在 350～500 ms 内响应尚未验证。

研发模式在首轮协议观察尚未完成时明确返回“读取中、本次未下发使能”，不把这一情况置为电机故障或断开后台读取。工厂快速验证在 read 通道等待首次观察，期间检查停止、租约和供电，等待有上界；读取完成后仅发一次使能。读取错误、结果不明不自动重试使能。仍保留身份匹配与 109 配置要求。

现场本次版本查询显示 0x31 固件字符串超时，0x1E 数值信息有返回；时间窗口差异是可复现的缺陷，未证明是该现场问题的唯一原因。此修复无法接收原生 SDK 窗口以外的回复，也不支持将数值版本臆测为固件代际。如果修复后仍超时，应采集只读版本查询的报文证据并核实固件查询能力。

控制路径（含电机故障复位）整体等待保持原先的 `0.25 + 0.7 × LRO 电机数` 上限，7 轴约 5.15 秒；逐条查询虽可等待 500 ms，但大量慢响应时整轮可能未赶在此截止时间内完成，仍会拒绝执行。这一上限避免本次更改增加原有控制等待预算，不代表已经验证或消除端到端请求超时后的全部未知状态。工厂快速验证最后一次检查至发送使能之间的既有并发窗口也未在此次消除。

## 现场确认的数值版本与独立协议规则

2026-11-12 用户确认当前左臂内 LRO_8462、LRO_6562、LRO_5550 电机的数值软件 `0.1.8`、硬件 `0.1.0`、协议 `0.0.1.17` 组合对应已验证的 108 旧控制协议。这是当前批次的现场声明，不是 `0x31` 固件字符串读回，也不是所有机器、型号、版本的通用映射。

参考整机上位机和固件脚本，监控表区分展示实际 `0x1E` 软件、硬件和协议数值，以及 `0x31` 原始固件读取状态。新代码默认不启用数字版本回退：只有当前用户状态目录下、所有者为当前用户且权限 0600 的 `config/lro-local-protocol-evidence.json` 允许启用经明确声明的规则；文件格式严格验证、不跟随文件符号链接。规则绑定有效站点配置摘要、部位、CAN 接口、ID、配置型号和数值三元组；`0x31` 必须为明确超时，`0x1E` 原始报文需本轮重新解码、与规则完全匹配且仍新鲜。发现109或其他冲突、缺项、协议不匹配或身份超期时不放行。匹配来源在状态中标识为 `local_numeric_evidence`，不生成原始固件字符串，不能用于固件刷写资格。

规则在配置工位时加载至该实例内存，修改或删除文件不会实时撤销；需按规程停测、失能并确认现场安全，正常关闭或断开并重新配置后才能撤销或变更。配置型号不是独立读取的硬件序列号，同地址、同型号且返回同版本的换件无法被软件自动识别；任何换电机或刷写固件应撤销声明并重新核实。协议变化或本地确认回读过期进入现有故障处理：保护阻尼也可能被拒绝，进而请求直接失能，而失能反馈可能未知。安装成功及模拟验证不等于机械支撑或真实设备安全验收。

在 1 号电机的一次被动 CAN 监听中记录到 `0x31` 请求和 `0x1E` 请求及后者回应，但在观察期未看到同 ID 的匹配 `0x31` 回应，不能证明其完全不支持该命令。按脚本设置的 1 秒 native/Python 窗口已在隔离环境研究，但未合入本次交付；更长窗口并不能凭现有现场证据解决上述缺失。

## 扫描后过早开放使能与上游驱动核对

2026-11-12 现场左臂扫描请求成功后，紧接着的使能请求返回 HTTP 409，说明固件与协议首轮读取仍在进行。`FactoryController.discover_motors()` 在各电机提供新鲜反馈后完成扫描。`MotorsPyBackend._open_transport_impl()` 启动独立的版本读取线程，逐台读取 `0x31` 和 `0x1E`。现场 `0x31` 每台等待 500 毫秒后超时，`0x1E` 随后成功，七台这一轮约 3.6 秒。旧桌面仅根据已发现状态开放按钮，且扫描完成回调无条件启用按钮。`FactoryController.enable_motors()` 在调用驱动使能前检查首轮读取，因此这次请求未下发使能。此后只读快照中七台均有新鲜 `0x1E` 读回，按本机现场核实规则选中 `legacy`，现场电机仍未使能。

`roboparty_deploy` 的 `main` 在核对时为 `95be3502dedfa8790f8e2cbb01feaf0fc4eb4934`，锁定 `roboparty_motors` 的 `a5c930a06a1648c2bc15c2c83ad0512ee9185258`（2.3.3）。另行核对的 `roboparty_motors` 主线为 `015ebe2340d9dfea4e1ddfa2c278378514ae584b`，相关 LRO 变更主要是增加经典 CAN 支持。两个上游版本的 `get_motor_param` 均通过 `E0 + 查询码` 发送 CAN-FD 参数查询，`0x1E` 是数值版本查询，运动反馈回调仅处理 8 或 12 字节的 type-1 状态，未提供 HMI 所用的 `0x31`／`0x1E` 版本响应缓存、逐台协议核实和版本就绪状态。当前 HMI 驱动使用同样的查询帧和上游的 V1.03 编码范围，并保留现场使用的旧协议编码。直接替换成上游库会失去本地版本读取 API 与逐台协议配置。此次保留现有 SDK，不改 CAN 帧、时间窗口或扭矩控制。

`factory_hmi/core/controller.py` 将同一首轮读取状态加入工位快照，桌面 `factory_hmi/desktop/app.py` 按该状态显示“读取固件与协议”并暂时禁用使能。实时快照报告完成后，按钮可再次供人员显式确认。使能请求在途时也持续禁用，避免实时状态刷新重新打开按钮或重复发请求。后台仍独立检查版本核实、实时反馈和其他使能条件。没有新增轮询、CAN 请求、自动使能或后台重试。
