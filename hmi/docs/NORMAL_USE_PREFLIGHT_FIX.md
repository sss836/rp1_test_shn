# 正常使用与启动预检回归修复

2026-10-28，老板确认原复位姿态正确、原预检正常，要求马上修复升级后的启动拦截，并要求交付安装后正常使用的版本，不默认切入 PLC 只读或测试配置。该最新要求调整了此前“缺少新增收尾参数阻止所有启动”的处理方式。

## 问题与修复范围

2.0.16 在 `FactoryController.arm`、`FactoryService.start`、`PlaybackController.start` 和工厂快速验证启动入口均把新增完整收尾参数作为硬前置。原工位 YAML 没有该配置，正常轨迹和复位即使通过旧预检，也先被“运动参数尚未核实”拒绝。

修复将原有测试准入和自动收尾分开：

- 原工位配置直接沿用原有预检，保留轨迹格式、电机数量、首帧实际误差、配置限位、播放速度和真实反馈/故障保护。
- 缺少自动收尾配置或明确未核实的模板不再阻止正常启动；没有填写假参数或将 verified/safe_to_disable 自动置 true。
- 如果明确配置了 verified=true，该配置必须完整有效；配置摘要不符、限位无效等仍阻止启动，不静默忽略损坏配置。
- 已核实自动收尾配置继续执行完整的补完当前周期、减速、回位、实际稳定确认及失能流程。
- 未配置自动收尾时正常结束补完当前周期，随后保持当前位置和使能，不自动失能；人工正常结束停止继续播放并保持位置。这条路径不宣称已经实现自动慢回下垂。
- 工厂模式在上述保持状态继续占用本窗口 CAN 并监控租约/供电保护，不提前执行清理失能，不影响其他窗口 CAN。独立软件失能和故障保护保留。

## 正式安装后的默认方式

正式种子配置为真实 modbus_tcp、control。已有用户的 PLC、CAN、电机方向、零偏、复位位及记录均保留，不将隔离测试数据写入工位 YAML。

安装器显式请求重启时沿用保存的模式，不再强制 --update-monitor。正常启动只建立原有连接与全 OFF 安全初始化，不自动使能电机或开始测试。显式诊断用只读和 mock 模式继续可用。

## 文件与接口

- `core/motion_completion.py`：`automatic_completion_parameters` 允许缺省；`motion_readiness.ready` 表示自动收尾就绪，新增 `test_allowed` 表示是否允许继续原有测试准入。
- `core/controller.py`、`core/service.py`：去除无条件的完整收尾配置前置，保留原有实际预检。
- `core/playback.py`：按照实际播放速度复查原有约束；运行中沿用当前反馈阈值；无自动收尾配置时进入 holding，并由控制器接续位置保持，不请求失能。
- `gateway/quick_run.py`：使用 test_allowed 判断启动；holding 状态保留 CAN 和监控，正常结束按钮不能将此状态直接清理失能。
- `desktop/app.py`、`desktop/quick_page.py`：区分轨迹文件检查与实时启动检查；说明 holding 未失能，不再无条件显示结束一定回位失能。
- `installer.py`：重启不追加只读参数；核对新实例身份、版本和电机未使能。
