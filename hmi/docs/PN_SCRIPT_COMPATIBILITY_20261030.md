# 已确认参数脚本的Pn兼容接入

本次修改依据用户确认的 `deploy_motorlro_params (1).py`，只实施软件、隔离验证和候选包，不执行安装、平台真实发布或真实电机操作。固定脚本SHA256为 `34f2214d52cf5e879e9ec169ec91725b22cdc99228a47d2671a491c9c85b0f3c`。用户报告此前多次写入成功，这支持采用该脚本作为参数和协议参考；本轮没有独立观察这些现场操作，也没有据此编造全部108/109适用映射。

## 1. 参数基线和精确适用性

- `factory_hmi/resources/motor-parameters/script-compatible-reference-v2.json`：四种型号、59项原始参数，其中27项Pn；与用户脚本AST逐项核对。保留用户确认原话、来源哈希及确认范围。没有完整版本实证的条目保持 `applicability=[]`、`confirmation=null`，状态为未发布参考，不能直接进入写入。
- `factory_hmi/motor_parameter_contract.py` 及平台相同契约 `backend/app/schemas/motor_parameters.py`：新增 `rp1-motor-parameters-v2`、固定 `protocol_profile=lro-pn-script-v1`。v1继续用于原常规参数，其Pn写入仍拒绝。v2发布要求来源为固定脚本、明确型号、原始固件/软件/硬件/协议完整版本及确认依据哈希。
- `tools/prepare_motor_parameters.py`：AST读取脚本，不导入、不执行。管理员提供实际完整版本适用表和确认依据，生成待审草稿；不自动发布、不连接设备。模板值仍可按既有管理员模板维护能力调整为新版本，不能由执行员临时输入帧或改值。

例如准备命令（文件必须由实际依据填写，不使用合成测试元组发布）：

```bash
python3 hmi/tools/prepare_motor_parameters.py \
  'user-supplied/deploy_motorlro_params (1).py' \
  /tmp/parameter-draft.json --script-compatible \
  --applicability /实际路径/型号完整版本适用表.json \
  --confirmation-evidence /实际路径/确认依据文件 \
  --confirmation-notes '实际型号、完整版本和本模板值的确认范围'
```

适用表结构为 `{"LRO_5550":[{"raw_firmware":"真实原始字符串","software":"真实软件版本","hardware":"真实硬件版本","protocol":"真实协议版本"}]}`；不得照抄占位字样。未核实的型号可不列。每个真实模板发布仍由平台真人管理员鉴权，执行员只能查询选择。

## 2. CAN脚本兼容适配

`core/motor_parameter_transport.py` 的 `ScriptParameterSession`：

| 动作 | 报文字节 | 数值处理 |
|---|---|---|
| 独立Pn读取 | `C0 11 Pn_hi Pn_lo` | 只发查询 |
| 明确确认后Pn写入 | `C0 10 Pn_hi Pn_lo value_u32_be` | 8字节，uint32原始整数 |
| Pn读取回复 | `FF FE 11 value_u32_be` | 不回显Pn编号 |

Pn值不套用USB/串口资料的16位寄存器定义，不再次乘倍率。常规参数维持原有大端、有符号范围和固定量纲；编码范围KP/KD不等于运行增益。`CAN_TIMEOUT=0`仍明确表示关闭保护，没有为了“能通过”暗改脚本值。

低层无上下文 `decode` 对无编号Pn回复仍返回 `association_unknown`；默认 `write_payload`仍拒绝Pn。只有任务引擎从已发布并核对过哈希、型号和完整版本的v2模板注入内部profile后，才调用脚本兼容会话。API请求只能选择目标索引与模板编号，不能直接注入profile、新值或CAN帧。

## 3. 单请求时序关联与失败恢复

任务预检查先核对持久隔离，再为每个所选Pn接口打开全ID被动接收socket并检查静默，不发送CAN命令；第一项普通参数操作前已能观察Pn竞争。每任务仅一个Pn会话，每接口保持一个接收socket；全部目标逐项串行，与固件维护共享占用，不跨总线并行。会话自身再拒绝并发read/write/close。接收观察整个接口，保留标准ID严格匹配，不把EFF/RTR/ERR标志去掉后当成合法回复。

每次请求前默认50ms静默观察；发送前原子保存 `in_flight` 标记；读取观察完整500ms窗口，写入后观察300ms再进入独立查询。返回第一条回复后不立即切换参数，第二条回复即使数值相同也视为关联不清。任务检查普通参数操作前后、版本核对前、正常终态及关闭前的Pn队列，避免迟到回复被静默丢弃。

超时、发送短写/异常、发送后取消、残留/重复/短Pn回复、其他ID或其他客户端Pn请求均停止批次，并持久隔离整个接口。报告记录原始帧、时间、接口/ID、参数、请求审计号、错误及 `association_method=single_flight_time_window`、`parameter_number_echoed=false`。审计请求号由本机生成，电机没有回显此号。

隔离目录使用各窗口共用报告根目录的 `pn-quarantine/`。更换参数/电机、关闭会话、新任务、重启软件均不清除。停止任务，正常断开电机连接，再由用户显式“断开CAN”，完整反馈确认所有指定接口已关闭后，将原记录追加归档至 `history/`，才解除主机通道隔离。关闭/状态查询/归档失败不解除。软件不会为恢复自动断开CAN、复位电机或控制供电。

**无编号协议的剩余限制：**若一个旧回复在前一次观察预算结束后，恰好进入后续请求的干净窗口，单凭这份报文无法证明其Pn归属。静默、串行、全窗口和隔离能拒绝已观察到的歧义，不能创造编号回显或厂家时序保证。显式CAN关闭仅重新建立主机时序边界，不证明设备端已无迟到回复或电机已重新上电。新会话仍检查静默和残留；真实固件时序及持久化需现场核验。

## 4. 读取、预览、写入与再次回读

`core/motor_parameters.py` 统一原有任务流程：

1. 选择当前配对实例的目标和管理员发布的精确适用模板；独立读取，只发查询，显示实际值与参考值、差异、单位、容差和来源。非read/归属未知不能授权写入，零项不能通过。
2. 预览实际旧值、新模板值和模板版本；明确确认后启动。读取和预览均限120秒，账号、有效配置、模板或实际旧值变化则拒绝；每台操作前重新读取实际版本。
3. 每项发送前先保存“发送中”，实际发出后立即独立回读。失败停止后续项，保留已写、发送不确定、已发未核验和未写。没有整体回滚或自动重试。
4. 每台写后弹窗请重新上下电。人工声明与再次回读各有独立动作和字段，声明不等于检测到供电变化。再次回读也要比较实际值和版本适用性，未执行就不能记录上电后核验通过。
5. 收尾保持总线与全局串行占用，直到终态报告保存、Pn会话和底层通道成功关闭。保存/关闭失败保留隔离，显式重试只重试收尾。收尾发现迟到Pn会把任务置为失败，不在关闭重试成功后改回通过。

`gateway/app.py` 负责本机租约、真人会话、有效配置、后台任务及共享隔离目录。平台模板发布/查询接口继续负责管理员发布、执行员和管理员查询、不可覆盖版本、幂等及内容哈希。此改动不进入采集CSV归档、审批或正式统计，也不改动平台原始测量事实。
