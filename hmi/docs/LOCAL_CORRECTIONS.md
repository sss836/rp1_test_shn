# 本地完整业务信息更正（不上传平台）

在“执行记录”中选中已完成记录，点击“本地更正…”。新版对话框使用三个可滚动业务页和一个审计页，支持下列信息：

- 基本信息：显示测试单号、SN、用例编号/版本、样机、部位名称/标识、实际测试人、工位、阶段、测试名称、实际对象。
- 时间与结果：本地判定及说明、判据版本标记、运行结束状态、结束原因、带时区起止时间、有效运行/总历时/暂停秒数、循环数。
- 记录质量与分区：有效/预期样本数、样本完整度、最大采样间隔、记录频率、故障区间计数、本机分区、记录范围/来源标签、软件/标定版本标记、备注和本地分析、同步、审批说明。

数字字段要求有限、非负且有明确上限，样本完整度为0～1，计数要求整数。日期必须包含时区，例如 `2026-11-03T17:30:00+08:00`，结束不能早于开始。业务字段均可清空为未记录，未知的数量或时间不会被当作0；原值仍保留在审计中。每次保存必须填写原因。

更正仅作用于本机业务视图、列表筛选、完整执行台账和CSV导出。判定、时长、数量或分区的手工更正不会重新分析原始测量，也不会进入自动统计或改动原始上传请求。本机分区更正标注 `LOCAL_CORRECTION`，只改工位仍不会自动改分区。导出保留原有列，并追加完整业务原值/本机值、操作人、原因和版本；数值0会明确导出，不再误作空白。长SN始终按文本处理，公式前缀仍进行转义。

显示测试单号是独立别名。内部 `test_id`、`execution_uuid`、文件路径、原始证据哈希、真实平台执行号、同步回执、审批状态和提交身份不能通过本地更正替换。本地同步/审批说明是单独备注字段，真实平台状态继续显示。CSV、封存manifest、summary、报告和执行包始终保留原始内容。

## 保存与审计

记录位于报告状态根目录 `local-corrections/<内部test_id>/v000001.json` 等，处于封存执行目录和执行包之外。新版使用 `rp1-local-correction-v2`；每版保存完整业务原值、更正前后值、变更字段、原因、操作人、UTC时间、原manifest SHA256和前一版本哈希。不存在覆盖或删除历史的应用入口。

旧版 `rp1-local-correction-v1` 的六字段日志继续按原有字段和哈希规则逐条校验；文件逐字保留。新版可在旧日志后追加v2记录，沿用版本号和哈希链。旧记录中没有保存的时间、质量和部位信息，从封存summary和execution context读取；缺失时显示未记录，不能猜测。

跨窗口/进程仍使用既有证据锁、`expected_revision`和`request_id`处理并发与重试。完整记录经flush/fsync后原子保存；重复请求不会重复追加。审计版本、哈希或原始关联异常时不应用更正，列表保留原值并提示异常。

更正落盘后刷新本地索引和台账。旧版索引会按视图版本标记逐条升级重建，不会沿用缺少时间、质量和业务字段的旧payload。重建完成才更新版本标记，中断后可重试。索引按更正后的本地日期、SN、工位和本机分区筛选；若台账写入失败，响应明确返回 `ledger_error`，已保存的版本不会丢失或被假称未保存。故障修复后显式重放同一保存请求可重建台账，不会追加版本。列表查询读取持久索引的上次有效视图，不隐式重写全量台账，也不代表实时证据完整性检查；外部改动审计文件后，需显式重建/刷新索引或打开更正页重新校验，异常版本不可再追加。

## 以后提交平台

本地保存不调用提交、重试归档、审批或上传唤醒。以后提交仍需要显式人工核实原始证据与有效平台工位。人员、工位、名称、对象和备注可用于核实表预填，但更正后的本机判定、时间、计数、分区标签不会被写回封存基线或冻结请求。

本机SN或显示单号不是平台关联身份。核实窗口继续并列显示原始SN与本机SN，平台归档仍使用原始身份；需要改变平台关联时应走已有平台核实流程。已上传、已归档或已批准记录也能追加本地业务更正，其平台内容和真实审批结果保持不变。

## 验证边界

检查使用合成文件、v1历史日志、隔离ASGI和offscreen Qt，覆盖新字段类型、未知值/0、时间与分区筛选、CSV原值/更正值、跨版本重放、并发冲突和真实状态保护。不运行设备，不以软件检查代替安装生效或现场硬件验收。
