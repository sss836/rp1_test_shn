# LRO 温度误显示与旧反馈失效处理

日期：2026-10-30。状态：修复源码与离线回归完成，未生成安装包、未安装、未进行真实设备验收。

## 结论与证据边界

“温度显示错误”和“旧温度继续显示为正常”是不同的缺陷，不能统一解释为温度传感器损坏，也不能凭它们的离线复现认定现场根因。原始审计及旧版本复现见 [软件审计](LRO_FEEDBACK_SOFTWARE_AUDIT_20261030.md)。

| 路径 | 直接触发条件 | 旧行为 | 当前源码状态 |
| --- | --- | --- | --- |
| A：回复类型误解码 | 同一 CAN ID 收到其他格式的回复 | 当作 type-1 遥测，温度错误且反馈计数推进 | 工作区此前已有类型过滤，本轮复核；本机安装的 3.0.0 尚不包含 |
| B：控制器保留旧年龄 | 未使能时 refresh_feedback/read_samples 抛异常 | 继续发布旧样本及原来接近零的年龄 | 本轮修改：按当前时间重算显示副本年龄，报告读取错误 |
| C：界面状态通道静默 | WebSocket 仍标记在线，但没有新快照 | 跳过备用读取，没有本地过期处理，旧值停在“正常” | 本轮修改：本地过期、静默降级、重复缓存不续期 |

用户已确认温度读取发生在未使能阶段，同一电机拆下且不作改动后单测正常。B 正好涉及未使能快照读取；A、C 也不要求使能。但现场缺少同一时刻的原始帧、异常日志及运行版本，仍不能确认是哪条路径被实际触发。

## 数据经过哪些环节

```text
CAN 接收线程
  → LroMotorDriver::canfd_rx_cbk：区分回复类型，解码遥测，推进该节点计数
  → MotorsPyBackend.read_samples：依据各节点计数计算最后收帧时间/年龄
  → FactoryController.snapshot：读取当前样本或保留上次证据
  → 服务/网关：生成快照，经 WebSocket 或 REST 发送
  → 桌面界面：合并服务端年龄与本地等待时间，决定能否展示为当前读数
```

CAN 帧到达、后端成功读取、界面收到快照是三个不同事件。连接标志不能证明持续收到了新数据，重新绘制界面也不能证明设备重新上报了数据。

## A：为什么会跳到 100°C

本机 3.0.0 的匹配源码虽然计算 fb_type，但没有先按类型分支，长度至少 8 字节的回复都沿用 type-1 的布局。温度取 data[6]-25；在其他类型里，data[6] 可能是另一字段。

离线注入先给合法 type-1、data[6]=71，结果为 46°C；再给同 ID 的 type-5、data[6]=125，旧接收函数给出 100°C，并推进反馈计数。这同时伪造了“温度”和“有新遥测”。type-2 的错误字段解析也已复现。

当前工作区 LroMotorDriver::canfd_rx_cbk 已先检查 ID 和长度，将 type-5 只交给查询结果处理，并直接返回；只有 type-1 进入位置、温度、error_id 解析和 feedback_count 递增。该修正此前已存在，本轮没有重复改写，也没有装入本机旧库。

这证明错误格式可以制造 100°C，不证明现场“100 往下降”的完整轨迹就是这样产生的。若现场始终只有合法 type-1，A 就不适用。安装修复时必须同时带上匹配的原生 SDK，不能只替换界面 Python 文件。

## B：为什么十秒前的 46°C 仍显示“正常”

旧 FactoryController.snapshot 在刷新/读取抛异常后直接忽略异常，继续使用 _last_samples。feedback_age_s 是建立样本时保存的数值，不是会自动计时的属性。

| 时刻（服务端单调时钟） | 实际事件 | 旧输出 | 修正后输出 |
| --- | --- | --- | --- |
| 100 秒 | 收到温度 46°C | timestamp=100、age=0 | 相同 |
| 110 秒 | 本次读取抛 OSError | timestamp=100、age=0，仍被视为新鲜 | timestamp=100、age=10，并有 feedback_read_error |
| 111 秒 | 读取仍失败 | 旧值、旧年龄继续保留 | age=11，不将缓存显示为当前读数 |
| 112 秒 | 读取恢复，取得 47°C | 恢复更新 | 新样本显示 47°C；原来非零设备故障码不会因读取恢复自动清除 |

本轮新增 MotorSample.with_feedback_age(now)，仅在快照出口建立显示副本，年龄取原年龄与“现在减最后反馈时间”中较大者。无效、缺失或未来时间不会按零年龄处理。原样本的温度、位置、故障码和观测时间不修改。

控制器新增 feedback_read_error，第一次失败记录 warning，连续失败不逐帧刷日志，实际读取恢复记录 info。读取错误或数据过期时不输出可当作当前值的关节换算位置。界面收到读取错误后立即显示“反馈读取失败；缓存值不可作为当前状态”，测量格显示“—”；已观察到的非零 error_id 继续保留。

这修正的是快照的证据和展示语义。已有控制线程、看门狗、失效门限及失能流程继续独立工作；本轮没有让界面定时器代替控制保护。

## C：为什么连接没断，数据却早就停了

旧界面每 5 秒触发备用读取，但 _ws_connected=True 时立即返回。若连接没有发出断开通知、服务却停止推送，界面既不调用 REST，也没有本地计时使旧值失效。

本轮增加两层处理：

1. **测量显示失效**：沿用界面 200ms 的显示门限，以服务端报告年龄、同一服务端快照时间减样本时间中的较大者，再加本地等待时长。窗口内一个 100ms 定时器检查过期；过期后清空当前测量格并显示等待新快照。实际执行还受 Qt 事件循环调度影响，不将它描述为硬实时保护。
2. **状态通道降级**：备用检查间隔改为 500ms；WebSocket 连续 1 秒没有新的遥测快照，即使连接标志仍为真，也启用 REST。因检查调度，实际请求时间可能在该门限之后。REST 或 WebSocket 收到新快照后，按每个节点的实际反馈年龄恢复显示。

重复发送完全相同的缓存快照、界面内部重画不会重置本地计时。服务端与客户端可能是不同电脑，因此不拿两台电脑的单调时钟直接相减，只比较服务端内部时间差，并另外累加客户端经过时间。

对象与请求生命周期：

- 两个 QTimer 均由窗口持有，创建一次，关闭窗口时停止；本地过期检查不发设备指令。
- REST 沿用线程池，_snapshot_pending 保证备用快照读取至多一个在途；成功或失败后的 finished 回调释放 pending，既有完成回调清理 worker 信号对象。没有每次计时创建线程。
- 本地过期重绘只更新测量表格和必要的失效显示，不重新应用旧快照里的登录身份、控制状态、故障弹窗或测试进度，避免旧缓存回写新操作状态。
- 租约心跳仍是独立通道，预算和控制失效保护未改变；状态快照恢复不等于运动保护解除。

200ms 是现有测量显示门限，1 秒是状态通道降级门限，冷启动发现的 5 秒是等待设备就绪预算，三者用途不同。延长扫描窗口不能修复错误解码或旧值显示。

## 哪些现象尚不能解释

- 合法 type-1 里位置持续变化、温度字节始终为 0x47 时，显示 46°C 是当前解析公式的结果；不能因为温度恒定就人为制造超时或修改偏移量。帧级新鲜性也不能证明设备内部 NTC 已重新采样。
- 若帧中温度字节变化、界面不变，才更直接支持解码/缓存/展示问题。需要同时记录帧类型，不能比较错误类型的 data[6]。
- B、C 会使一批缓存测量共同停止更新，不能单独解释持续更新的同节点角度与停住的温度。
- 当前 SDK 的 0x07 映射为 DRV_ERROR，过温映射为 0x01。0x07 不是由界面看到温度高而自行生成；旧版误解码可能连 error_id 一起解释错，须以合法帧核对。恢复读取不会自动清除已观察到的 7。
- 原审计附加发现的“同总线重复 ID 配置未被拒绝”尚未在本轮修正；默认短臂配置未发现重复。物理设备实际重号仍需现场核对。
- “单测正常、整臂异常”可能改变触发条件，但不能据此确认软件、供电、总线或传感器中的任何一个完整根因。CAN 错误不能简单描述为只有温度字节损坏而同帧其他字节正确。
