# 手臂 LRO 电机温度异常与 0x07：初步诊断记录

日期：2026-10-30。状态：代码核对与现场排查建议，根因尚未确认。

后续补充：[软件审计](LRO_FEEDBACK_SOFTWARE_AUDIT_20261030.md)已核验本机安装包与工作区的差异，并完成非遥测帧误解码、旧样本年龄和界面静默路径的离线验证。下文“没有核验安装版本”等说明属于初步排查阶段，后续软件核对结果以该审计为准；现场根因仍未确认。

## 现场描述与证据边界

- 用户描述：同批雷塞电机装在一条手臂上测试时，温度反馈卡住；上电后显示温度跳到约 100，再下降，随后出现 0x07；拆下来单独测试正常。
- 用户补充：0x07 只在本项目上位机显示，尚无厂家调试软件的独立读数；厂家未提供可用的 Linux 调试软件。
- 用户进一步确认：所有读取均发生在没有使能的阶段。本次异常应按未使能上电/读取问题排查。
- 用户再次强调：同一台电机拆下来后，没有做任何改动，单独测试一切正常。应保留这一对照，不应假定用户刷写固件或调整参数后才恢复。尚未明确“没有任何改动”是否也包括原供电线、CAN 线、其他总线节点连接和控制程序完全保持不变，仅解除机械安装。
- 尚缺：具体型号与固件版本、是否冷机、单个还是多个关节、时间尺度、原始 CAN 报文、实际供电波形、单测和整臂测试使用的软硬件差异。
- 本次核对的是当前工作区源码，基线提交为 d04ef76；工作区存在未提交改动。没有核验故障工位实际安装的软件包、加载的原生驱动及正在运行的进程版本。
- 没有执行现场 CAN/PLC 通信、使能、运动、故障复位、固件升级或安装操作；没有完成硬件复现或验收。

## 当前代码实际行为

| 文件与函数 | 已核对行为 | 能说明什么 |
| --- | --- | --- |
| `hmi/motors/src/drivers/lro/lro_motor_driver.hpp`，`LROError` | 0x01 为 MOTOR_OVERHEAT，0x03 为 UNDER_VOLTAGE，0x04 为 ENCODER_ERROR，0x07 为 DRV_ERROR | 在此 SDK 中，0x07 是驱动器故障分类，不能直接当作过温、编码器断线或电机损坏的根因 |

| `hmi/factory_hmi/desktop/app.py`，`_render_snapshot()` | 新鲜反馈且 error_id=7 时提示 DRV_ERROR、温度可能冻结；过期反馈隐藏测量值 | 提示语只是故障提醒，不是某款固件冻结温度的实测结论 |

## 对症状的合理解释

用户已确认未使能，因此本次测试中的带载发热、运动卡滞发热和位置环增益振荡不应作为最初温度跳变的首要解释。机械安装仍可能通过线束挤压、接触、板件受力或机壳电气连接影响异常；未使能也不代表驱动控制电路、测温电路或通信收发器已经断电。

若进一步确认电机已经冷却、刚上电，显示值便在几秒内从约 100 明显下降，则应优先核查测温采样、启动初始化、供电参考以及报文来源和解析。此时温度显示不足以证明绕组真的发生相应温变，也不能仅靠外壳温度排除内部局部过热。尚未确认冷机和时间尺度，不能将这一推断写成实测结论。

同一台电机未作改动，拆离手臂后单测恢复，提高了装机条件触发问题的嫌疑。不能假定用户更换了电源、线缆或控制程序；需要明确实际保持不变的条件。

若原供电线、CAN 线、其他节点和读取程序也完全不变，只解除机械固定，则优先检查安装后线束/连接器受力、机械压迫引起的条件性接触缺陷，以及机壳与支架接触形成的电气路径。若单测时减少了其他节点或换用了独立供电/线束，则共享电气条件仍是首要分支。单测正常不能单独证明电机内部不存在受力触发的缺陷，也不能据此认定整臂一定是 CAN 干扰。

目前只能提出以下待验证分支，不能把它们写成已确认因果链：

1. 整臂共用电源或回流路径出现瞬态压降、噪声或地电位差，影响电机内部采样、初始化或驱动状态。
2. 装机线束拉伸、弯折、压伤或连接器接触不良；安装受力还可能暴露内部接插件、焊点等条件性缺陷。
3. 多节点 CAN-FD 的终端、电缆分支、ID 冲突、速率配置或负载与单测不同，造成丢帧、错误来源关联或缓存不更新。
4. 电机本身未作改动，固件变化不作为首要解释；若两种测试使用不同上位机、原生库或初始化顺序，仍需核对解析和状态处理差异。不能在未确认时假定两种程序不同。
5. 用户确认本次所有读取发生在未使能阶段，因此本次先降低带载、制动未释放导致运动发热、摩擦与增益振荡的排查优先级；若另有使能后的独立症状，再单独分析，不能混入本次已确认的触发条件。

CAN 有帧校验，不能笼统地把温度跳到 100 解释成“干扰把温度字节随机改掉”。需要区分丢帧、错误节点/ID、协议不匹配，以及设备在干扰条件下自行生成异常测量值。

## Linux 下如何独立核对

不依赖厂家 Linux 软件，也能用 SocketCAN 原始报文记录核对“发送什么、收到什么、软件显示什么”。记录应覆盖异常前后的 CAN 接口、收发方向（应结合工具能力、SocketCAN 本地回环和报文类型确认，不能只凭 CAN ID 猜测）、时间、CAN ID、FD/BRS 标记、长度、完整数据字节，并与上位机温度、error_id、反馈年龄和使能状态对时。

对与当前源码兼容的 type-1 帧：

- 第 1 字节，即 `data[0]`，若为 `0x27`，则高 3 位为 type-1，低 5 位为故障 7。
- 第 7 字节，即 `data[6]`，若为 `0x7D`（125），按当前公式显示为 100 ℃。
- 若原始报文已包含这两个值，说明上位机显示有对应的接收字节依据；仍需排除 ID 冲突、错误节点归属与协议版本差异。此证据不能单独定位驱动器内部故障原因。
- 若原始温度字节变化、上位机温度不变，应检查现场实际加载的驱动、缓存与界面更新。
- 若报文接收时间和其他字段持续推进，只有温度字节长期不变，则优先排查设备测温/上报链路；恒温时字节不变本身并非故障证据，需结合异常跃变、独立测温和故障状态判断。
- 若该节点整帧不再到达，则优先查供电、连接与通信；若同总线多个节点同时停止反馈，优先查共用部分。

不要为抓取报文同时开启第二个发送控制指令的主站；被动记录不应发送使能、清错或运动命令。需要厂家细分故障时，应保留首次故障和历史记录，再由匹配型号的官方工具或技术支持读取，避免先复位丢失证据。

## 推荐的对照顺序

所有改线、检查安装件与电阻测量，都应在测试停止、负载可靠支撑、电机失能并确认断电后进行；不通过拆除保护接地来验证假设。重新上电观察应保持失能，不以真实运动作为首轮诊断条件。

| 对照 | 条件与观察 | 结果如何解释 |
| --- | --- | --- |
| 原位单节点 | 保持原机械安装，采用单测时已知正常的供电和通信线，仅保留该节点并核对终端 | 若恢复正常，优先检查整臂原供电、线束、总线或控制配置；尚不能区分其中哪一项 |
| 分别恢复原供电、原通信 | 一次恢复一项，记录症状与原始报文 | 确认问题是否随特定供电或通信条件出现；注意换线也可能改变回流路径 |
| 保持原电气条件再改变机械安装 | 使用安全支撑和厂家安装要求进行条件对照 | 仅在机械固定/布线受力变化时改变，才提高装配、线束应力及内部条件性缺陷的嫌疑 |
| 逐个恢复其他节点 | 保持 ID 唯一、接线和终端正确，依次增加节点 | 确认是否与某节点接入、节点数量或共同上电相关；不能直接认定为总线负载 |
| 同条件替换电机 | 型号、参数、安装与线路可比时更换已知正常电机 | 故障随电机走则提高电机内部问题嫌疑；留在工位则提高线路/供电/安装条件嫌疑 |

供电检查要测到电机插头端的启动和故障瞬态，不能只看电源面板平均读数；上位机测量字段也不能替代独立电气测量。

高速 CAN/CAN-FD 通常在总线两个物理端点各用 120 Ω 终端，不能每个节点都加。对于断电后仍接通的两只被动终端，CAN-H 与 CAN-L 间通常约为 60 Ω；内置可切换/有源终端需按设备说明解释读数，不能凭该电阻值单独判定链路健康。[NI 官方终端说明](https://www.ni.com/en/support/documentation/supplemental/09/can-physical-layer-and-termination-guide.html)。
