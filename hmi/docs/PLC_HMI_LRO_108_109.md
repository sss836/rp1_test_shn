# PLC 上位机：108 / 109 混装、版本升级与参数检查

改动基线：RP1 PLC 上位机 `v3.0.28`（`a31910c`）。本文所述为基于该版本的源码改动。现有发布包不会因本次代码变动而变化。

当前 109 基准为 [RoboParty 2026-10-28 15:37 构建](https://github.com/Roboparty/roboparty_motors/blob/a5c930a06a1648c2bc15c2c83ad0512ee9185258/firmware/L5N_RZT2L_CAN_CDH2_V5.0.0.109_202610281537_release.lsepbin)，文件 `L5N_RZT2L_CAN_CDH2_V5.0.0.109_202610281537_release.lsepbin`，501316 字节。已核对 Git blob `4d7dfd1dd71f78e0de33e7dcd44a365eff4ce076` 与 SHA256 `7277645da5e2d461e0339e87e21b5603abcb13065416fb416a1e279d48eb966a`。上位机按 SHA256 选定此构建，缺少时不会回退到 10 月 21 日或其他 109。管理员验证将来的同代构建后，可在重新签名的 v2 策略写入 `preferred_109_sha256` 并提供对应转换条目；文件本身仍必须有独立的签名发布。不同代固件仍要单独做兼容验证。

如果已是 109 的电机只回读 `5.0.0.109`，跳过记录仅表示实际代际是 109，不能证明它已刷过 1028。对本次升级的电机，回执分别保留实际写入文件哈希和独立版本回读。

## 现场如何操作

1. 在工位应用实际模块、CAN 接口和电机 ID，连接后等待电机实际版本读回。从「电机版本 / 固件下载」查看每台的完整版本、配置及实际启用的驱动协议。
2. 「整模块 108 → 109」按当前模块有效配置列出全部电机，只把实际版本已核实的 108 纳入升级。已是 109 单列为跳过；任何一台身份不明会阻止整模块开始。若只需处理一台或部分电机，在版本表选中电机后进入「升级选中电机」，或在维护窗口按接口、ID、关节名勾选。单选模式不要求其他电机的版本已知。
3. 从「查询兼容固件」下载对应型号的签名固件。只有一份匹配时自动选中，多份时明确选择；仅下载的固件资源库不进入升级列表。预览显示实际目标、目标版本、目标协议、SHA256 和兼容证据。确认后逐台刷写。每台写完需由人员重新上下电，确认后单独回读；实际版本与签名目标完全一致才进入下一台。
4. 「检查选中电机参数」打开参数窗口。勾选所需电机，点「只读检查选中电机」。108 读取 KT、KP/KD、位置、速度、转矩、电流和 CAN 超时等普通参数，显示实测值。109 还读取所给脚本中该型号的 Pn 参数，分列显示实测值、单位、脚本参考值和差异。不同固件的参考不混用；缺少响应或响应归属不明不会被记作一致。脚本对照是诊断信息，无需已发布模板，不能作为写入来源。原有管理员模板读、比对、明确确认后写入功能保留。

维护沿用真人会话和当前工位租约。工位必须停测、失能、结束归零/位置保持且 CAN 就绪。维护不自动使能、切换 PLC 或电源；同时禁止另一个任务占用该维护通道。回读前的人工确认只记录现场声明。取消、掉线或重启不自动重放刷写。

## 为什么不能整站切换为 109

用户指定的 [RoboParty 部署参考提交](https://github.com/Roboparty/roboparty_deploy/commit/95be3502dedfa8790f8e2cbb01feaf0fc4eb4934) 锁定 [电机驱动 a5c930a](https://github.com/Roboparty/roboparty_motors/tree/a5c930a06a1648c2bc15c2c83ad0512ee9185258)。其 LRO V1.03 的 MIT 速度/转矩量程、故障掩码和反馈字段与 v3.0.28 使用的旧驱动不同。按节点切换才能在同一 CAN 上让 108 与 109 各用自身量程，避免把 V1.03 的使能位当故障，或把 Iq 电流写成力矩。

- `motors/src/drivers/lro/`：新增每个电机的协议配置，单台与批量控制按节点编码。V1.03 解码驱动使能位、故障码、Iq 电流与可用的母线反馈；8 字节帧没有母线附加值。
- `scripts/rp1_limb_common.py` 和 `factory_hmi/core/backend.py`：读取工位配置，在使能前核对真实回读和驱动能力。原始版本简称只用于识别代际，不能推导三段数值版本、硬件或四段协议。身份未知或不符时可继续只读诊断，禁止用猜测的量程发运动命令。
- `factory_hmi/core/playback.py`、`core/telemetry_hub.py`、`gateway/local_curves.py`：Iq 单独显示和保存；没有核实的换算关系时，109 力矩显示为缺测。工厂快速验证需要力矩的项目不会凭电流或缺失值判通过。原来保存的 108 曲线数据不改写。
- `factory_hmi/core/zeroing.py`：V1.03 标零单独报告「指令已提交，待重新上电核验」，不会用旧版的即时位置判断报成功。上位机不自动复位，现场仍需核验零点。

工位的 `lro_protocol_profiles` 按 `motor_id` 原配置的顺序配置，每个槽位对应一个电机。未指定的旧节点走 `legacy` 并按实际版本验证；109 节点需填 `profile: v1.03`、`raw_firmware`、`numeric_software`、`hardware`、`protocol` 和 `verification_evidence`。字段值来自该型号/硬件实际的 `0x31`、`0x1E` 回读及核实资料；本文不提供可能被误用于现场的示例数值。升级后按电机更新配置，重新连接再核对。附件里的命令不应代替上位机的工位配置和维护流程。

## 刷写资格与回执

`core/motor_maintenance.py` 按配置哈希及“接口 + 电机 ID + 型号”绑定选择。开工前复查计划内的全部 108 和跳过的 109，写每台前再次读取源版本；发现变化会停止，并保留未执行项。模式、计划、跳过项、刷写字节数、人工确认和实际回读写入实例状态目录下的 `motor-maintenance/<job_id>.json`。只读参数结果保存到 `motor-parameters/<job_id>.json`。

108 → 109 模式需要两份证据：现有 `rp1-motor-firmware-v1` 的可信签名固件，以及 `rp1-lro-ota-compatibility-v2` 的精确转换记录，二者都由可信电机固件公钥校验。可使用 `tools/prepare_motor_ota_policy.py` 准备签名文件，部署在上位机状态目录的 `config/motor-ota-policy.json`，也可通过 `RP1_MOTOR_OTA_POLICY` 指定路径。v2 每条沿用 v1 的源型号、硬件、协议、原始版本、软件版本、OTA 协议及证据字段，新增 `target`，内含 `raw_version`、`software_version`、`hardware`、`protocol`、`firmware_sha256`。适用记录绑定具体文件哈希，不能用两份都叫 109 的二进制相互替代。允许同一三段软件数值、不同四段固件标签的明确转换；回读仍逐项匹配。其他固件的 v1 通用维护路径保持。

已核对参数附件 SHA256 与仓库脚本参考完全相同。参数附件不提供逐台固件读回和硬件适用表；上游仓库的固件文件名也不提供这些字段。真正启用升级需要现场取得精确版本证据、签发适配清单和策略，并在试验工位验收。固件预览、下载与参数诊断不会自动填补这些证据。
