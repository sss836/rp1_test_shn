# local14：整批固件写完后统一上下电与一键核验

## 问题与证据

用户现场 local13 中，can0 ID1 完成501316字节传输和设备校验，但ID3/4/5/6/7仍pending。任务状态awaiting_power；人工确认时间已落盘，状态仍awaiting_power。这不是点击事件丢失，而是旧后端把人工确认与启动回读拆成两个独立动作。

local13只将产线参数路径改成整批写完后统一上下电，固件路径仍在每个目标的循环内等待上下电和版本回读。这处流程未同步，是本次修复的原因。

## 更新后的顺序

1. 按原规则核对整批所选目标、源版本、固件文件及SHA256。
2. 串行写入所选电机，每台保存传输字节数、原始校验应答及复位回执。已是109且未选中的电机保持跳过。
3. 一台写完立即继续下一台，行状态“已写完，等待其他电机”；此时不弹上下电提示。
4. 所选台全部写完后，整批进入awaiting_power，只提示一次统一上下电。
5. 人员完成后点击“已统一上下电，开始核验”。一个HTTP请求内持久保存全批人工声明和readback_requested，成功落盘后才唤醒后台线程。
6. 逐台独立读取完整固件、软件、硬件和协议。每台单独判定；某台版本不符/读取超时仍继续读取其他台，完整展示核验结果，不重刷。

单选也走同一流程。写入阶段任一台失败则停止后续写入，前面已写台标记written_unverified，未启动台标记not_run；不把已写完当成已核验成功。读回阶段失败不会把其余已通过台改成失败。

## 文件级实现

- `factory_hmi/core/motor_maintenance.py`：ModuleFirmwareMaintenance.start写入power_cycle_scope=batch；_run将人工等待移到写入循环之外。_verify_written_target逐台保存回读及判定。acknowledge/readback旧接口继续兼容，但批次必须全部确认。confirm_power_and_readback新增单请求动作：鉴权、校验job_id、确认整批处于等待态、落盘声明与回读请求、唤醒读取。
- 同一job重复确认返回已受理状态，不重复读取或写入。确认落盘失败时恢复内存快照、不设置读取事件，允许用户重试。账号/会话与实例权限仍由既有网关边界核对。
- 重启不会恢复写入；written_awaiting_batch_power等进行态落为interrupted_unverified。终态保存、维护锁释放和CAN独占的原有顺序不变。
- `factory_hmi/gateway/app.py`：增加固件维护confirm-power-and-readback动作，继续采用登录/租约/服务/任务锁顺序及本机维护令牌。
- `factory_hmi/client.py`：将新动作加入客户端允许列表，保留本机local=true路由。
- `factory_hmi/desktop/motor_maintenance_dialog.py`：更新说明、启动确认文案、批次一次提示和状态表。仅保留“已统一上下电，开始核验”可见操作，隐藏旧的第二个回读按钮；按钮本身就是明确人工声明，不再二次弹窗询问。

## 长时行为与异常

刷写与回读继续在factory-motor-maintenance线程运行。Qt按现有计时器查询状态，后台等待人工操作通过Event，不占用GUI线程。后台等待每100ms检查取消和权限；人工等待不设自动结束时间，更不会自动操作PLC或供电。单台OTA传输保持产线协议300秒预算，读版本保持每项0.5秒预算；本次未改变底层CAN协议。

写进度按原规则最多约250ms保存一次，并在每台传输结束强制保存。选择、待写、已写、已核验、通过分别显示，解决“有5台待写却显示未执行0台”的理解问题。HTTP确认请求不执行CAN读取，只提交已落盘的后台任务，所以点击后立即返回并由进度轮询展示核验。

## 验证与交付边界

新增隔离测试覆盖7台无中途上下电、混装跳过109、一键全批确认与回读、重复点击幂等、人工确认落盘失败恢复、错误账号/任务拒绝、中途写失败、回读失败继续核对其他台、重启不续写，以及实际HTTP路由、客户端动作列表和Qt按钮。继续运行local13的固件/参数/多工位相关回归。

产线参数原脚本、四型号数值及本机固件文件没有变化。本次软件开发不打断现场旧批次，也不把旧批次静默切换为新流程。安装需要旧任务结束和现场停机条件，完成后以真实进程版本和健康检查为准。真实整批刷写和一次上下电的现场验收仍需在新版本中执行。
