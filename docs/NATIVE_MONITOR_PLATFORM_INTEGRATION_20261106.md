## 使用后的实际行为

打开整机上位机先显示与大屏一致品牌和浅蓝网格的登录页，填写平台 HTTPS 地址、可信 CA（内部证书需要）及现有平台账号。首次账号必须先改密码，才开放平台业务。密码、Cookie 和 CSRF 只在进程内存中，不保存为登录文件，不带进浏览器 URL。原生窗口与浏览器分别登录同一账号体系。

完整登录前不启动本地 station、不恢复机器人连接；只读本地历史可访问。首次完整登录后进入原有连接流程：工厂快捷入口打开原工作台；quick-connect 初始化原电脑后台并进入 SSH 配置／已有连接恢复；不会自动使能电机或启动测试策略。平台退出／到期只使平台任务暂停，本地已经开始的采集、记录和控制不随之停止，已登录过的实例仍能进入“本地监控与工具”。

“研发测试”和“工厂测试”分别提交证据、查询档案；“本地监控与工具”是共享的原有工具，不因点击分区而更改本地数据归属。上位机的“打开大屏”带域和具体档案身份，平台仍独立检查浏览器登录与访问权限。

## 研发证据如何保存与传输

源端继续保存既有 PostgreSQL `monitor_recordings` 和 `monitor_recording_samples`。新增导出器只接受当前系统用户拥有、权限 0600 的连接文件；事务 `READ ONLY`、`REPEATABLE READ`，连接／SQL 预算各 5 秒，分批 256 点读取。它不实例化原 Store／Recorder，不建源表、不改源数据、不调用聚合曲线 API。

只有 `ended_at` 已写入的监控记录可作候选。**监控记录结束不证明硬件测试结束**；有效运行时长、循环、异常、结论仍需人员核实。输出格式固定为 `time_s,sample,rp1_recording_json,rp1_sample_json,<指标…>`：保留记录 ID、来源、指标、源单位、原始观测时间、原序号、完整采样 payload 及其原 SHA256。逐点核对哈希；缺值不补零，序号跳号不补点，时间不改为等间隔。

平台严格重验元数据、哈希、时间／序号／数值对应及封存数量。模拟来源和篡改文件不能达到研发 READY；缺失点／序号缺口按实际质量标注，仍保留原件供核查。JSON 证据列上限 256 KiB，普通字段 4096 字符，指标最多 256 项。源单位未提供时明确标记，不凭键名猜单位。

原始 CSV 和派生曲线文件存放平台仓库之外的可配置 `ARCHIVE_ROOT`；PostgreSQL 保存身份、索引、哈希、归类、核实及审批版本。导出副本放本机独立平台状态目录，SQLite 只保存任务／路径／哈希／回执等元信息，不把几十 GiB 文件放入 SQLite BLOB 或一次性装进内存。原始源 PG、本机导出及平台原件均不因上传成功而自动删除。

研发调用链：

```text
人工选择已结束 PG 监控记录
  → 只读一致快照／流式精确导出
  → 人工选择 7 UUID + 填写实际事实 + 核实并明确提交
  → POST /api/v1/archive-imports（HISTORY / RESEARCH，采集事实未知）
  → PUT /archives/{id}/content?offset=N（每段最多 4 MiB）
  → POST complete → 独立 archive-worker 哈希校验／曲线转换 → READY
  → POST /archives/{id}/verify-and-submit → PENDING
  → 独立批准／驳回；批准后按既有访问权查询正式执行
```

7 UUID 为 campaign、cycle、segment、asset、configuration、test_case_version、station。界面只用平台返回的真实上下文；已有合法上下文不因账号没有编辑计划权限而被隐藏，已发布旧版用例也不会被最新目录版本替换。实际工位与上下文固定一致。测试人员文字与登录提交人分别保存；不默认通过，不用观测跨度充当有效时长。

## 权限、审批、并发与失败恢复

人员账号、测试计划访问权、数据核实和数据审批各自独立。原生平台使用当前会话 Cookie＋CSRF；没有借用旧 ingestion、通用附件、执行包或机器人凭据上传。管理员／执行员可以提交；工厂审核员只能访问允许的工厂业务，不得从原生入口读取研发源 PG。服务器继续做最终权限检查，隐藏按钮不代替服务端鉴权。

工厂上传与审核是两个显式操作，现有角色允许自审。工厂审核使用预期 revision 和稳定幂等键；竞争决策只允许一个版本成功。驳回后明确重新提交追加新版本，保留原件、旧值、核实／审批人和理由。研发沿用既有原子核实送审及审批事务；驳回后按当前版本重新核实送审，待审／驳回数据不进入正式统计。

研发待传任务冻结目标 URL、账号、域、源记录、文件、7 UUID 和人工事实。重试不把工厂文件改标签发送到研发，也不偷偷改旧归档。服务器每次回执都核对 archive ID、execution UUID、owner、域、origin、大小和 SHA；同 SHA 已有待审／批准记录时，只有上下文与核实事实相同才能确认原任务，否则明确报冲突并保留待处理任务。丢失分段回执时先取服务器 `received_bytes` 再续传；回执不确定不是“上传失败后重建一个执行”。

本机平台业务一次一个后台 worker；界面主线程不做网络／PG 导出。操作冻结会话代次、来源和域，晚到回调不能污染换号后的界面。401、到期或降权清平台缓存；取消关闭当前 socket，窗口关闭等待 worker 自然结束，不销毁活线程。原本地采集／控制线程仍沿用上游生命周期。

网络单次请求有 15 秒 socket 总截止；等待 READY 的轮询循环预算为 45 秒，已发出的一次 HTTP 仍受自己的预算控制，因此不能承诺整操作绝不超过 45 秒。DNS 解析仍受系统 resolver 限制。日志保留安全机器错误码，不输出密码、Cookie、源连接串或服务器原始敏感错误正文。

默认单导出 50 GiB、研发 pending 64 GiB／128 项、导出目录 64 GiB、磁盘预留 512 MiB，均可在服务构造参数中调整；不自动清理证据。任务容量检查在 SQLite 事务中完成。工厂沿用原独立 outbox 的 32 MiB／64 项 pending 预算与轻量回执保留规则。预算不等于全进程 RSS 或全目录恒定大小；源 PG 的长期容量规划仍需独立制定。

## 已知边界与现场步骤

1. 平台账号登录和机器人在线是两种状态。新原生页没有自动常驻 presence；实时在线仍由原独立桥接根据真实来源上报。只有上传汇总时新建的机器人默认离线，不能据登录／上传成功点亮绿灯。研发也没有把监控录制自动投影为正在进行的正式测试。
2. 人员平台会话默认 8 小时，具体以服务端为准。到期重新登录同账号后继续待传任务，不承诺无需人员值守的几千小时人员会话。
3. 工厂 source 首次绑定提交账号，目前没有管理员移交／解绑入口。换班／停用账号需要后续受审计授权迁移，不能删除历史或改 source 编号抢占来源。
4. 精确导出可以处理长记录，但源 PG 大表 count／max 若超过 5 秒会明确失败，源数据保留；现场需按真实规模调整索引／预算。没有把聚合曲线替代原始证据，也没有实施源数据库自动分区／保留策略。
5. 工厂汇总只包含关键结果；研发归档保留选择记录的完整原点。两者都不能被描述为“整机上位机已改成只保存关键信息”。原保存策略未改，几千小时磁盘容量必须按实际指标数／频率评估。
6. 本次隔离软件验收不代表真机联调或几千小时稳定性验收。安装前确认现场停止状态、正常退出旧实例并核对进程；安装成功也不能代替核对新进程版本和健康状态。不强杀控制进程、不删锁或运行数据。
