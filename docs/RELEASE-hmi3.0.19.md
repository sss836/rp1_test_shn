# 上位机 3.0.19：执行记录的三项修复

完整版本：`3.0.19+ubuntu24.04.recordfix1`。目标系统：Ubuntu 24.04 amd64。

## 1. 平台一直显示上传中

真实平台核对显示，两条工厂记录已经登记归档和分段，但接收字节均为0，日志中没有文件分块PUT。原因在 `hmi/factory_hmi/sync/reliability_platform.py`：`archive_segment_chunk()`使用分段接口，而`_call()`的二进制校验只允许旧的单文件接口，HTTP请求发出前就被本机拒绝。后台保存为同步失败，重新提交核实时又因已有冻结请求产生409；409是后续保护提示，不是首次失败原因。

现精确放行两类归档PUT，保留UUID、分段序号、非负偏移、4MiB块大小、认证和原始文件哈希约束。重试继续原执行身份、冻结请求和分段偏移，不删除原件或生成另一条测试。两条现有记录的原提交账号均为16F；更新后选中原记录点击“重试归档”，不需要重跑机械臂测试。

## 2. 多个测试同时结束时互相等待

确认存在的阻塞路径是：全局单线程收尾队列中，一个采样线程无期限退出等待会拖住后面的窗口；服务报告又无期限等待记录完成。另一个风险是后台封存异常迟到调用设备故障处理。

现在复用每次执行已有的报告等待线程独立收尾，采样退出等待预算5秒，服务记录收尾等待预算7秒；一次性锁和recorder身份校验防止重复收尾及旧任务误标新一轮完成。超时保留原始文件、活写线程及占用，报告明确失败，不能冒充封存成功、释放所有权或覆盖下一轮。播放结束后的存储异常只登记记录错误，不再触发迟到设备指令；运行中的保护逻辑保留。

这是对已发现软件路径的修复，尚未通过现场多台架并发长测；不能保证任意操作系统、磁盘或驱动故障下永不卡顿，也不能据此确定此前机械臂跌落的完整原因。

## 3. 本地更正信息不足

原限制同时存在于6字段核心白名单、请求大小、固定对话框和历史视图。现扩展为40项业务信息，分为基本信息、时间与结果、质量与分区三组滚动页，并保留原值与审计页。覆盖显示单号、用例、SN、部位、人员、工位、阶段、判定、时间、时长、循环、样本、质量、版本与备注；允许清空为未知，数值0独立保留。

旧v1更正文件逐字保留，可沿原哈希链追加v2记录。列表、筛选、CSV和本机台账使用同一更正视图，并同时保留原值。旧索引按视图版本逐条重建；扫描与台账导出按条目/分页处理。内部执行身份、原CSV、封存报告、冻结上传及平台真实同步/审批状态独立保留。本地更正不自动改变正式统计。

历史列表索引是上次有效视图；更正窗口读取、保存以及索引刷新/重建时校验审计。列表查询不隐式重写台账，也不宣称每次翻页都实时校验全部磁盘证据。
